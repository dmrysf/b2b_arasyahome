# Deployment

## Branches

- `main`: source of truth.
- `deploy`: generated by GitHub Actions; contains only the verified artifact: `dist/` (with `release.json` and `dist/SHA256SUMS`), the deploy and rollback scripts, `.cpanel.yml` and a package-level `SHA256SUMS`. No editable source. The server needs neither Node nor Vite.

## CI gates (`.github/workflows/b2b-build-deploy.yml`)

`verified-release` publishes to `deploy` only after every gate passes on `main`:

1. `quality`: frozen install, typecheck, ESLint with zero warnings, unit tests, production build verification.
2. `browser-smoke`: Chromium against the production build with an in-memory API double (desktop and mobile viewports, RO and TR, no horizontal overflow, no page errors, no foreign hosts).
3. `real-api-e2e (mysql-8.4)` and `real-api-e2e (mariadb-10.11)`: Chromium against the real Operations API pinned in `e2e/operations-api.ref`. The private source is checked out with the read-only deploy key secret `STAFF_REPO_DEPLOY_KEY` (public half registered on `dmrysf/staff_arasyahome` as a read-only deploy key named for B2B CI).
4. `verified-release`: `pnpm verify`, `release.json` (`commit`, `version`, `builtAt`, `preview: false`), content checksums, the validator with the expected SHA, a deploy dry-run, then the push to `deploy`.

Repository variable `VITE_B2B_API_BASE_URL` must be `https://api.arasyahome.ro`.

## Prerequisites

B2B 0.2.0 needs Operations API 2.8.0 with migrations 008 and 009 live (0.1.0 needed 2.7.0 and 008), and the production `ARASYA_ALLOWED_ORIGINS` must contain exactly `https://staff.arasyahome.ro`, `https://dashboard.arasyahome.ro` and `https://b2b.arasyahome.ro`. `php bin/readiness.php` reports `migrations`, `iam_applications`, `b2b_company_permissions` and `cors_origin_b2b.arasyahome.ro` OK. Never deploy a B2B version before the API it needs. `e2e/operations-api.ref` pins the API commit the real-API suite runs against.

Rollback: `scripts/cpanel-rollback-b2b.sh --previous` returns to the previous verified release. B2B 0.1.0 keeps working against API 2.8.0 (it ignores the new endpoints), and API 2.8.0 can itself be rolled back to 2.7.0 while the additive migration 009 stays in place; B2B 0.2.0 must then be rolled back first, because its Companies screens need 2.8.0.

## Server layout

| Path | Purpose |
|---|---|
| `$HOME/public_html/b2b.arasyahome.ro` | B2B document root, the only directory the scripts write live files to |
| `$HOME/arasya-b2b-releases/<sha>` | Retained verified releases (mode 0750, outside `public_html`) |
| `$HOME/arasya-b2b-releases/{active-release,previous-release,release-history.log}` | Pointers and history |
| `$HOME/repositories/b2b_arasyahome` | cPanel Git checkout tracking `deploy` (remote `git@github-b2b-arasyahome:dmrysf/b2b_arasyahome.git`, read-only deploy key `~/.ssh/b2b_arasyahome_deploy`) |

The scripts refuse any document root not named `b2b.arasyahome.ro`, any release storage inside `public_html` or the document root, and every Dashboard, Staff, API, config, backup, WordPress, Trendhome, OutletPerdele and Lace Secret root. `.well-known/` and `cgi-bin/` are never touched.

## Deploy

1. Confirm the latest `B2B Build & Publish` run on `main` is green and `deploy:dist/release.json` names that `main` SHA.
2. In cPanel Git (`b2b_arasyahome`): **Update from Remote**, then **Deploy HEAD Commit**. Over SSH:

   ```bash
   uapi VersionControl update repository_root=$HOME/repositories/b2b_arasyahome branch=deploy
   uapi VersionControlDeployment create repository_root=$HOME/repositories/b2b_arasyahome
   ```

3. Check: `https://b2b.arasyahome.ro/release.json` names the expected SHA with `preview: false`; the entrypoint sends HSTS, the CSP with `connect-src 'self' https://api.arasyahome.ro`, `X-Frame-Options: DENY`, `X-Robots-Tag: noindex` and `Cache-Control: no-store`; every referenced `/assets/*` file returns 200 with the immutable cache policy; `/assets/` gives no directory listing; a deep link such as `/oricare` returns the application.

Activation is additive: hashed assets are copied first, `index.html` last, so a failure before the switch keeps the previous release serving.

## Rollback

```bash
cd $HOME/repositories/b2b_arasyahome
DRY_RUN=1 /bin/bash scripts/cpanel-rollback-b2b.sh --previous   # validates and names the candidate
/bin/bash scripts/cpanel-rollback-b2b.sh --previous              # or an explicit retained source SHA
```

Rollback re-validates every checksum and the provenance of the retained release, then records the change in `release-history.log`. B2B has no database; rolling it back never affects the API, Staff or the Dashboard.

To withdraw B2B entirely without touching the API: remove the B2B grants in the Dashboard (root keeps access by definition), or roll the Operations API back to 2.6.0, which keeps working on the migration 008 catalog. Removing `https://b2b.arasyahome.ro` from `ARASYA_ALLOWED_ORIGINS` (from the timestamped configuration backup) blocks the browser application immediately.
