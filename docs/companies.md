# Companies V1 (B2B 0.2.0)

Companies is the first B2B business module. It manages wholesale companies (B2B customers): their identity, fiscal data, contacts, addresses and internal notes, with a full activity history. Arasya employees use it internally; it is not a customer portal. Everything later (orders, the current account, projects) will hang off the company identity created here.

The data lives in the Operations API (`operations-api/src/B2B`, migration 009, API 2.8.0) as its own module, separate from production, Staff, source integrations and the IAM internals. The API contract is documented in `staff_arasyahome/docs/b2b-companies.md`.

## Screens

| Path | Screen |
|---|---|
| `/companii` | List: search, status and country filters, keyset pages of 50 ("Încarcă mai multe") |
| `/companii/noua` | Fast creation: legal name, country and tax identifier; an optional first contact and first address |
| `/companii/{id}` | Detail with separate sections: Company information, Contacts, Addresses, Internal notes, Activity |

The `{id}` is the server-generated UUID. The human-readable code (`B2B-000123`) is displayed and searchable, but it never identifies a company in a URL or a request.

## Company identity

| Concept | Rule |
|---|---|
| `id` (`company_uuid`) | Stable public identity, generated by the server; carries no business meaning |
| `code` (`B2B-000001`…) | Generated by the server from a concurrency-safe database sequence; immutable; never typed or generated in the browser |
| Legal name | Required; stored as entered (only outer spaces are trimmed); not unique |
| Commercial name | Optional |
| Country | ISO 3166-1 alpha-2, required; names are shown in the interface language |
| Tax identifier | Required: **CUI / Cod fiscal** (RO), **Vergi numarası** (TR). Unique per country after normalization: upper-case, without spaces, dots, dashes or slashes, and without a leading VAT prefix of the same country (so `RO 12.345.678` equals `12345678` in Romania). The same raw number in another country is a different company. |
| VAT number, registration number, website | Optional; the website must be http or https |
| Status | `active` or `inactive`. Companies are deactivated and reactivated, never deleted. |

A duplicate tax identifier is refused with the stable conflict `COMPANY_TAX_ID_ALREADY_EXISTS`. The UI explains it neutrally and, for a viewer, links to the existing company. Companies are never merged automatically. No external tax-registry lookup is performed.

## Contacts and addresses

- **Contacts.** Several per company, each with name, job title, e-mail (stored in lower case), phone, primary flag and status. At most one primary contact per company. The database enforces this with a unique marker, so two racing requests cannot both win. Choosing a new primary steps the previous one down. Deactivating the primary contact leaves the company valid, with no primary contact.
- **Addresses.** Several per company. Each is typed: `billing` (Facturare / Fatura), `delivery` (Livrare / Teslimat), `office` (Birou / Ofis) or `other`. An address has a label, country, county or region, city, postal code and two address lines.
  - At most one primary address per company **and type**: a company can have a primary billing and a different primary delivery address.
  - Billing and delivery addresses are never assumed to be the same.

## Internal notes

Internal notes are commercial information for authorized Arasya employees only, edited in their own section. They are never sent to Staff, production, WooCommerce or any customer. The activity history records that the notes changed, never their text.

## Permissions

Every request needs the B2B application gate (`b2b.access`, unchanged) **and** one company permission. Both are checked by the server.

| Permission | In the UI |
|---|---|
| `b2b.companies.view` | Companies menu, list, detail, contacts, addresses, notes, activity |
| `b2b.companies.create` | "Companie nouă" |
| `b2b.companies.update` | Edit company data and notes; add, edit, deactivate and reactivate contacts and addresses |
| `b2b.companies.manage_status` | Deactivate and reactivate the company |

`GET /b2b/access` reports which of these the identity can use, and the UI offers only those actions. The server still decides every request.

- Without any company permission, the Companies module is not shown.
- With create but not view, the employee can register a company but sees no company data.

Roles are composed by administrators in the Dashboard role editor (Dashboard 0.5.1 shows the permissions in Romanian and Turkish). B2B has no permission-management screen of its own. Root has everything through the existing root semantics.

## Concurrency

Every company, contact and address carries a server version. Saves send `expectedVersion`. If another employee saved first, the API answers `409 COMPANY_CHANGED` (or `CONTACT_CHANGED` / `ADDRESS_CHANGED`) and writes nothing. The UI then works like this:

1. It keeps the employee's form exactly as typed and explains the conflict.
2. **Încarcă versiunea actuală** loads the current version. Fields the employee edited keep their values; untouched fields take the current values, so another person's change is never reverted.
3. Each edited field that now differs from the current version shows its current value.
4. The employee reviews and saves again on the new version.

## Idempotency

Every mutation sends an `Idempotency-Key`. A double click, a browser retry or a slow-network retry of the same change reuses the same key, so the server applies it once and writes one activity event. Changing the content starts a new key, and a completed change never reuses its key. Keys are generated in memory (`crypto.randomUUID`) and never stored.

## Activity

The Activity section lists the immutable B2B history of the company, newest first:

- stable action keys, localized for display (for example `company_created`, `contact_deactivated`, `address_updated`);
- the contact or address concerned;
- the names of the changed fields;
- the employee;
- the time.

It is separate from the IAM audit, which stays about identity and security. Changed values, contact details, addresses and notes are never stored in the history.

## Privacy and browser storage

Company, contact and address data is only requested from `/b2b/companies` endpoints and only kept in memory while a page is open. Nothing is written to `localStorage`, `sessionStorage`, IndexedDB or cookies; the only browser-storage entry remains `arasya.b2b.locale`. Errors are shown from localized codes; server text is never displayed.

## Not in this module

There are no orders, order history, product history, prices, discounts, balances, debts, payments, credit limits, invoices, inventory or 3D. No financial or risk labels exist: the UI never calls a company a bad payer or high risk. Detail responses carry no empty placeholder objects for modules that do not exist.

## Future relationships

- **Orders.** A B2B order will reference `company_uuid` and snapshot what it needs when placed: company name, tax identifier, the selected address and the selected contact. Later company edits never rewrite historical orders, and historical orders never depend only on live company text.
- **Current account.** Receivables, payments and balances will be their own milestone, attached to `company_uuid` without changing the company identity.
- **Inventory.** The company domain is independent of inventory. Future order lines may link products to `inventory_product_id`; companies never depend on it.

## Tests

- **Unit** (`tests/companies.test.tsx`):
  - request shapes, CSRF and Idempotency-Key headers, and strict response mapping;
  - permission filtering, intent keys, routes, form helpers and countries;
  - SSR states in RO and TR, and centralized texts.
- **Browser smoke** (`e2e/b2b-companies.spec.ts`, production build with an API double):
  - list, search, filters and server pagination;
  - creation with contact and address, the duplicate tax identifier and the concurrent-edit review;
  - status, contacts, addresses, notes and activity;
  - the permission variants and an API failure that keeps the list;
  - 360, 390, 768 and 1280 px without horizontal overflow.
- **Real Operations API** (`e2e/real-api.spec.ts`, MySQL 8.4 and MariaDB 10.11):
  - a controlled identity with B2B access and a role holding the company permissions;
  - creation with a server code, contact, address, edit and activity;
  - a stale edit (409) and its review; deactivate, inactive filter and reactivate;
  - TR and a phone screen;
  - B2B access removal, deactivation and root;
  - no production change, and no request to any other host.
