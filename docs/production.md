# Operations + Staff integration V1 (B2B 0.5.0)

Finalization is unchanged: freeze commercial data and post the receivable. Only a separate “Trimite în producție” / “Üretime gönder” action creates production. The order stays commercially finalized. The confirmation explains that cancellation becomes permanently unavailable after submission, including after completion.

The card at the top of an order detail reads canonical progress through GET `/b2b/orders/{UUID}/production`: submitted state, operational reference, submission time, canonical stage and ordinal/14, stage change time and completion time. Refresh and return-to-tab revalidate the server state. No owner/stage controls exist in B2B and no authoritative production state is stored in the browser.

POST to the same path sends only `{expectedVersion}` plus the existing HttpOnly session, CSRF and actor-scoped idempotency key. A failed network attempt retries the same intent/key; it cannot create a second production order. API uniqueness and row locks also protect distinct-key races. All eligible line types transfer, with unchanged whole-line meters (`quantity=4`, `meters=13.5` stays **13.5**, not 54). Company/type/notes come from frozen manufacturing snapshots, not subsequently changed live identities. Prices, balances and allocations are never sent to Staff.

Permissions are separate: `b2b.production.view` and `b2b.production.submit`. Each additionally needs B2B application access and `b2b.orders.view`. Application access stays outside ordinary roles. Migration 012 grants neither permission to existing roles. An administrator may add just these two permissions to the explicitly approved B2B commercial role; do not grant Staff/production/admin/finance permissions as a workaround.

Compatibility and manual deployment order: API 2.11.0 with additive 012 → Dashboard 0.5.4 labels → Staff 2.3.2 context rendering → B2B 0.5.0. Before any live migration use the existing DB/config backups and official `php bin/migrate.php`, then official seed/readiness. Existing external-source warnings are unchanged. This implementation task **does not deploy or run any production migration/acceptance write**.

Rollback: retain migration 012, handoff links, all operational/commercial/financial rows and audit. B2B may roll back to accepted 0.4.1 (`ce4f9cf15b5debb82946f20afe9d83759748353f`, deploy `e11f3e31e3e7a0f32558eafaf7cb48eef8f6b942`) while keeping guarded API 2.11.0. Never use unguarded API 2.10.0 with commercial writes enabled after a real handoff: it lacks the new cancellation guard. Role revocation alone does not constrain Root. Prefer a forward correction; an unavoidable old-API rollback needs a separately verified isolation of **all** B2B commercial writes, including Root, before activation. Do not drop additive history.

Live acceptance after human deployment: controlled B2B role/account only; draft has no submit; finalize alone creates no production; explicitly submit RON/EUR frozen orders, including an inactive live company; verify 3 line types, unchanged meters/totals/account; retry and double click produce one link/order; check Staff scan/claim/transition and B2B refresh/completion; cancellation returns `ORDER_ALREADY_IN_PRODUCTION`; verify narrow permissions, RO/TR, 1440/768/390/360 and reduced motion. Stop on a defect and fix/test/push/verify a new Git release, never hot-edit production.
